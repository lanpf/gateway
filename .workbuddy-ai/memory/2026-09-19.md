## 设计审查（用户提问）：访问段/准入段为何接收 command 以外的参数

### 订正：command 的语义

我上一轮把"签名证据不能来自 prepare 段"错说成"不能进 `AccessStageCommand`"——**这两件事不同**。用户的反问是对的：`AccessStageCommand` 的语义是"已到达访问段"，而不是"prepare 段的产出快照"。

**command 的语义**（从全仓命令归纳）：**一个具名意图 + 执行它所需的事实**，是应用层的用例输入。`PreparationStageCommand` 的注释就是"请携带这份证据，不新增任何事实"；`SaveAppAccessCommand` 是"按此修订保存这条 App 内容"。

**由此得到的判据**：command 装**事实**，方法参数装**协作者**。

| 输入 | 性质 | 归属 |
|---|---|---|
| snapshot / endpointMatch / RequestEvidence | 准备段产出的事实 | command ✓ |
| ClientSignatureEvidence | 匹配后采集的事实 | **应进 command**（现状是散参数） |
| Set<RateLimitRuleId> applied | 准备段产出的事实 | **应进 command**（现状是散参数） |
| Supplier<CompletionStage<SubjectAuthenticationOutcome>> | 按请求构造的延迟协作者 | 留参数——它不是事实，且必须延迟调用（歧义短路时不得触发认证） |
| ClientVerificationOutcome / SubjectAuthenticationOutcome | 本段异步产出 | 留参数——是产出不是输入 |

反证：服务的稳定协作者（`clientAuthenticator`/`evaluator`/`policies`/`clock`/`quotas`）都走构造器，不走方法参数——`subjectAuth` 之所以例外，是因为它闭包了本次请求的凭据，属"按请求构造的协作者"。

结论：我原答的"两个真问题"仍然成立，但性质要改——**`signatureEvidence` 与 `applied` 本该进 command**（不是"可以"而是"应该"，因为它们是事实），`AccessStageCommandService` API 不自治那条不变。

## 三阶段交接链修复（用户指出「access 的 output 应该是 admit 的 input」）

用户指出三阶段应是 prepare → access → admit 的链式交接。核实后两条边情况不同：

**边 1（prepare → access）**：功能上通，但 `Prepared` 在 `AccessSnapshotWebFilter` 被拆成 4 个 exchange 属性、到全局过滤器再拼回命令，类型关系只存在于程序员脑中。**已收紧**：新增 `PREPARED` 键承载 `PreparationStageOutput.Prepared` 本身；删掉 `SNAPSHOT`（唯一消费者 `PolicyAwareBearerTokenConverter` 只拿它判空）、`ENDPOINT_MATCH`、`EVIDENCE`、`APPLIED_IP_RULES`；`ENDPOINT` 保留为唯一匹配端点的非规范化视图（安全链转换器 + `LocalPolicyWebFilter` 用）。接入段命令现在在唯一一处从 `prepared` 投影。

**边 2（access → admit）**：**确实是断的**。`admit` 收的是 `AccessStageCommand`——与接入段同一个输入，内部再调 `access.evaluate`，所以 `AdmissionStageCommandService` 是接入段的包装而非一个阶段。**已修**：新增 `AdmissionStageCommand(AccessStageOutput access, Set<RateLimitRuleId> applied)`；`admit(command)` 为段本体（输入只来自接入段产出，可独立调用与测试），`admit(accessCommand, subjectAuth)` 为请求路径组合入口（先跑接入段再准入）。组合必须留在 application 层——`IngressTask` 是包私有，传输层造不出来，而取消要跨两段级联。

**重要：这不是严格链**。`applied`（准备段的配额执行记录）**绕过接入段**直接到准入段——只有准入段读它（跳过 pre-auth 已执行的规则）。若强行走链，就得在 `AccessStageOutput` 上加一个接入段从不使用的字段。所以数据流是 DAG（带一条跳边），不是链。已写入 DOMAIN §4.3/§9。

新增测试 `shouldAdmitTheAccessOutputWithoutRunningTheAccessStage` 覆盖段本体入口。

## 阶段交接统一规则：命令包裹上一段的成功产出

用户追问「access→admit 收的应该是 `AccessStageOutput.Allowed` 吧？那 prepare→access 也应该是 `PreparationStageOutput.Prepared` 吧？」——两条都成立，已改。

**确立的规则**：每条边只携带上一段的**成功产出**，且命令**直接包裹**它而非重述字段。

- `AccessStageCommand(PreparationStageOutput.Prepared prepared, ClientSignatureEvidence signatureEvidence)`
- `AdmissionStageCommand(AccessStageOutput.Allowed access, Set<RateLimitRuleId> applied)`

拒绝不进管道：准备段的拒绝在边缘终止，接入段的拒绝由**组合入口**直接送终态（`admit(accessCommand, subjectAuth)` 里判断 `instanceof Allowed`）。因此 `AdmissionStageCommandService` 的段本体 `admit(command)` 只处理成功路径。

**我上一轮的判断被推翻**：我曾主张「投影而非包裹，因为投影让接入段输入与准备段产出的形状解耦」。这个论证站不住——`AccessStageCommand` 当时已经带了 `applied`（接入段从不读的字段），所以"投影=只含本段所需"本来就不成立。改用包裹后：
- 交接带类型：接入段命令不可能由准备段产出以外的东西构造
- `applied` 不再需要独立字段（= `prepared.quota().executedRuleIds()`）
- 适配器构造命令从 5 个实参降到 2 个

**代价（刻意接受）**：命令会携带本段不读的字段（配额记录）。定位修正为：命令是「**管道在那一刻知道什么**」，不是「本段需要什么」。已写入 DOMAIN §4.2。

测试同步：`IngressStagesTest` 的 `command(app, applied)` 把 applied 放进 `QuotaExecution`——更贴近生产（生产就是从 `prepared.quota()` 取）。

验证：`mvn -o -B clean test` → BUILD SUCCESS，12 模块全绿，285 项测试 0 失败。

## AccessStageOutput 与 AccessDecision 的对称性修复

用户指出两点：(1) `AccessStageOutput` 与 `AccessDecision` 抽象重叠；(2) `Denied` 带 snapshot version 而 `Allowed` 不带，不对称、不优雅。

**两点同源**。原定义：
```java
record Denied(AccessDecision.Denied denied) implements AccessStageOutput { }        // 包裹决策，但不加任何东西
record Allowed(AccessGrantedContext context, EffectivePolicy, HeaderPolicy, Map) { } // 解包决策，且丢掉 snapshotVersion
```
所以拒绝分支是纯重复包装，允许分支是**有损的重新编码**——丢掉 `snapshotVersion` 直接违反 DOMAIN §2.4「两种决策都携带请求所持快照版本」。

**修法**：两个变体都**持有**决策，接口暴露 `AccessDecision decision()`：
```java
public sealed interface AccessStageOutput {
    AccessDecision decision();
    record Denied(AccessDecision.Denied decision) implements AccessStageOutput { }
    record Allowed(AccessDecision.Allowed decision, EffectivePolicy policy, HeaderPolicy headers,
                   Map<RateLimitDimension, String> dimensions) implements AccessStageOutput { }
}
```
关系从「平行层级 + 有损重编码」变成「包含」。顺带修掉该类型被打乱的 Javadoc（原文 "Only an allowed denied carries executable post-authentication access"，是合并事故）。

**一个我明确判定为"不该做"的方向**：把 `AccessStageOutput` 整个删掉、让接入段直接返回领域 `AccessDecision`。看似能消除重叠，实际做不到——阶段输出必然要携带决策**加上**下游需要的东西（策略/Header/配额维度），删掉它只是把这些字段搬到 `AdmissionStageOutput`，重叠换个地方出现。**"领域决策 + 应用附加物"这个形状是固有的**，正确的处理是让包含关系显式，而不是消灭它。

**遗留（仍待决，与本次相关）**：`PolicyResolver` 调用点在接入段，但 DOMAIN §1.1/§1.3/§4.3 把「授权及绑定解析」与「headerPreparation」都划给准入段。代码把 §4.3 的两项工作都做在了 §4.2 的服务里。注意：即使把这两项搬到准入段，也不会消除上面说的固有形状——那是个独立的能力放置问题。

组件改名连带：`AccessStageOutput.Allowed` 的组件 `context` → `decision`，消费点改为 `allowed.decision().grantedContext()`；`Denied` 的组件 `denied` → `decision`（原写法 `denied.denied()` 很别扭）。

验证：`mvn -o -B clean test` → BUILD SUCCESS，12 模块全绿，285 项测试 0 失败。

## 删去 AccessStageOutput.Allowed.headers 冗余字段

用户指出 `Allowed` 里的 `headers` 就是 `policy.headers()`，为什么要单列。确认冗余：`AccessStageCommandService.decide` 里就是 `new Allowed(allowed, effective, effective.headers(), ...)` 直接传的。

**为什么该删**：`PolicyResolver.resolve` 保证 `EffectivePolicy.headers()` 非 null（内部 `selected.headers() == null ? HeaderPolicy.defaults(null) : selected.headers()`），所以 `policy.headers()` 是唯一真源；单列等于存了第二份值，且没有任何机制阻止它与策略不一致。

**为什么它此前是"安全"的**：`Allowed.headers` 本来就是 `effective.headers()` 的拷贝，所以"依赖 resolve 保证非 null"这个前提**早就成立**了——删掉字段不引入新的依赖，只是不再重复。

消费点只有一处生产代码（`TrustedRequestContextGlobalFilter` 的 `headerWriter.write`）加两处断言，改为 `allowed.policy().headers()`。

顺带注意：`EffectivePolicy` 本身允许 null headers（`PolicyResolver.resolveNodes` 会构造中间态），所以这个非空保证**只属于 `resolve` 的输出**，不是类型级不变量。已写进 `AccessStageOutput` 的 Javadoc 与 DOMAIN §4.2，免得后人误以为 EffectivePolicy 自带非空约束。

验证：`mvn -o -B clean test` → BUILD SUCCESS，12 模块全绿，285 项测试 0 失败。

## EffectivePolicy → ResolvedPolicy + 解析器合并中间态

用户批准后执行。`EffectivePolicy` 更名为 `ResolvedPolicy`（与 `PolicyResolver.resolve` 配对，用代码库自己的动词而非需要解释的形容词）。

**同时修掉"一个类型两种不变量"**：原来 `resolveNodes` 也返回 `EffectivePolicy`，且其 `headers` 可能为 null（没有任何匹配的 bundle 带 headers 节点时）；`resolve` 再包一层补默认值。同一类型既表示"选中的节点"又表示"最终生效的策略"。

改法：把 `resolveNodes` 并入 `resolve`，就地累加、只构造一次，Header 默认值在构造前代入；`ResolvedPolicy` 构造器加 `Require.notNull(headers)`。这样非空保证从"`resolve` 的输出性质"升级为**类型级不变量**，`AccessStageOutput` 的 Javadoc 措辞也随之修正。

**"Policy" 词族的澄清（用户提问：字面看只是策略，太难理解）**：统计出 109 个含 Policy 的标识、949 处引用——**家族级改名不可行**（且大量无关：`AbortPolicy` 是线程池拒绝策略、`unmappedTargetPolicy` 是 MapStruct 选项）。判断为**文档问题而非命名问题**：同一个词被用在三种粒度上。已在 DOMAIN §3 加「命名约定」表——前缀 `Policy*` = 组合机制（Config/Bundle/Binding/Resolver/Resolved），后缀 `*Policy` = 单个能力节点（Timeout/CircuitBreaker/Cache/Header），并点名 `RedisFailurePolicy`/`LocalPolicyWebFilter` 等不属于本词族。

## 命名判断：单值能力节点保留 `*Policy` 后缀（未改代码）

用户问「能力节点可以不用 policy 吗」。复盘后**我上一轮给的理由是错的**——我说"后缀是 DOMAIN §3 的单值节点标记"，但 `RateLimitRules` 这个节点本来就不带后缀，所以那条约定并不统一。

**真正的理由**：后缀区分**配置与配置对象**。`CachePolicy` 是"怎么缓存"的设置，`Cache` 则是缓存本身；`TimeoutPolicy` 是连接/等待/总时限，`Timeout` 则是超时事件。去掉后缀会让名字指向被配置的东西，而不是配置——这是语义问题不是风格问题。

**因此判断**：节点侧不动。若日后要削减 "Policy" 的出现次数，**组合机制那五个才是目标**（`PolicyConfig`/`PolicyBundle`/`PolicyBinding`/`PolicyResolver`/`ResolvedPolicy`），因为那里 "Policy" 才真的没说清"配置什么"。备选是改用文档自己的词「能力」——`CapabilityComposition`/`CapabilityBundle`/`CapabilityBinding`/`CapabilityResolver`/`ResolvedCapabilities`，但 5 个类型、名字变长，需用户拍板。

已把「为什么节点保留后缀」与「这不构成统一约定」写进 DOMAIN §3 的命名约定表下方。
