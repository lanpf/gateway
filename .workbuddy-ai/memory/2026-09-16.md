# 2026-09-16

## Revision / SnapshotVersion 值对象迁移收尾 + 遗留项修复

用户先在 application 层引入了 `Revision` 与 `SnapshotVersion` 值对象（要求组装 service 时不用裸 long/String），迁移是半程的，构建断裂。本轮补齐并回答设计问题。

### 值对象现状（迁移完成后）
- `com.cloud.gateway.domain.access.Revision(String value)`：非空、trim 的源修订令牌。
- `com.cloud.gateway.domain.access.SnapshotVersion(long value)`：正数快照版本（0 非法），取代原 `AccessSnapshotVersion`。
- 贯通范围：`AccessDefinitionWithRevision(value, Revision)`、`AccessSnapshotWithRevision(snapshot, Revision)`、`AccessSnapshot.version() → SnapshotVersion`、`WritableAccessDefinitionRepository.compareAndSet(Revision, T) → Revision`、`AccessSnapshotPublisher.compareAndSet(Revision, snapshot) → boolean`、`AccessSnapshotHistory.find(SnapshotVersion)`、`RollbackAccessSnapshotCommand(SnapshotVersion)`、editing 层全部 `save`/`set*Status` 返回 `Revision`。
- **边界**：`gateway-api` DTO（`AppsApiView`/`ClientsApiView`/`EndpointsApiView`/`DefinitionSaveApiOutput` 的 `String sourceRevision`，`SnapshotApiResponse` 的 `long snapshotVersion`）保持裸类型作为线上协议；转换只在 `gateway-interfaces` facade 内做（入参 `new Revision(...)`，出参 `revision.value()`）。
- **已收口**：`AccessSnapshotAssembler.assemble(SnapshotVersion version, ...)`；版本递增由 `assembleUpdate` 内部 `new SnapshotVersion(Math.addExact(previous.version().value(), 1))` 完成，调用方不再计算版本。`AccessSnapshotPublication.validateAlreadyPublished` 直接透传 `observed.snapshot().version()`（原先解包再重包），`PropertiesAccessSnapshotProvider` 的常量改为 `SnapshotVersion INITIAL_SNAPSHOT_VERSION = new SnapshotVersion(1)`。至此 application 与 infrastructure 层不存在裸 long/String 标识；`gateway-api` DTO 仍保留裸类型作为线上协议。

### 本轮修掉的缺陷
1. `ObservedAccessDefinitions.revisions()` 返回类型 `List<String>` → `List<Revision>`。
2. `PolicyConfigCommandService`/`AppAccessCommandService`/`ClientAccessCommandService`/`ClientCredentialCommandService`/`EndpointAccessCommandService` 的 `save`/`set*Status` 返回 `Revision`；`AccessDefinitionWriter.update`、`AccessDefinitions.restore` 内部变量同步。
3. `DefaultAccessDefinitionCommandFacade`：7 处 `expectedSourceRevision` 统一包成 `new Revision(...)`，出参 `.value()`；`saveEndpoint` 把 `EndpointAccess` 拆成扁平参数（与 `SaveEndpointAccessCommand` 的 content-only 形状一致）。
4. `config/application.yml` 的键 `gateway.policy-definition` → `gateway.access-definition`（`GatewayPolicyDefinitionProperties.PREFIX` 已改名，旧键导致绑定为空）。
5. **示例快照 `examples/gateway-policy.yaml` 内嵌 contentHash 过期**：`43c00446…` → `fd603a9c3e085bc97c193b2ddf641320c39951cda77f5b64684046399e212a4a`（规范化投影改名后哈希变化；canonical hash 再次变更，外部开发快照须重新生成）。
6. **`NacosAccessSnapshotHistory.find` 用 `==` 比较 `SnapshotVersion` record**（引用比较，永远不相等）→ 改 `.equals`。
7. `NacosAccessSnapshotStore` 的 `catch (DomainException)` 已成死代码，删除。

### 用户指定项
- 第 1 项 `api/facade/policy`：用户明确暂不修改，未动。
- 第 2 项：**按用户意见彻底回退**。`PolicyYamlCodec` 只报自身层级的 `INFRA_TECH_POLICY_DESERIALIZATION_FAILED`，不区分失败原因；三个 decode 调用点各自按语境转换为 `INFRA_ACL_NACOS_CONTENT_INVALID`，领域校验原因作为 cause 保留在堆栈中。原先新增的 `AccessContentErrors`（沿 cause 链还原 `DomainException`）已删除——理由：领域错误码 `ACCESS_SNAPSHOT_INVALID` 没有任何下游消费方（仅 domain 单测断言），异常原因本来就在 cause 里可见，用异常图遍历做控制流属于多余机械，且让三个调用点行为不一致。顺手给 `NacosAccessSnapshotHistory.find` 补上同样的语境转换（原先裸抛 `INFRA_TECH_*`），并消除其重复 decode。基础设施层不重新分类领域异常。
- 第 3 项 LKG 文件存储：`writeFully` 循环写（`FileChannel.write` 可能少写）、写完 `force(true)`、移动后 `fsyncDirectory`（不支持时 debug 记录）、`ATOMIC_MOVE` 不支持时改为「先 copy 再 force 目标」的降级（原先直接非原子 move 可能在崩溃时留下截断文件）。
- 第 4 项限流适配器：新增 `RedisRateLimitProperties.acquireTimeout`（默认 500ms），`RateLimitQuotaAdapter` 用 4 线程有界池 + `Future.get(timeout)` 界定阻塞调用，超时/池满/依赖故障统一降级为 `unavailable`（交给 `RedisFailurePolicy` 决定），超时后 `cancel(true)` 中断 worker。**关键点**：`ExecutionException` 需解包，只有 `DataAccessException` 才转 `unavailable`，其余 RuntimeException/Error 原样抛出——否则会把编程错误吞掉（原测试 `shouldNotSwallowProgrammingErrors` 正是在守这条）。新增超时用例。
- 第 5 项 `NacosAccessSnapshotStore.compareAndSet`：远端 CAS 成功后本地投影失败不再向外抛异常（会被调用方当成「未发布」而重发），改为记录 error 并返回 true；Nacos 变更通知与周期恢复循环会重试本地接纳。
